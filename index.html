Recovery key entropy is sent to their server

The recovery key uses a standard BIP39 2048-word English wordlist — 12 words, 132 bits of entropy. Brute-force is infeasible. But the code sends recoveryEntropyB64 to Aside's backend. If their server is compromised, every recovery key is too.

recovery-CBf919w0.js → standard BIP39 wordlist (2048 words)
recovery key form → recoveryEntropyB64 sent via tRPC mutation
"account can't be recovered if pass lost" → single point of failure

Both extensions inject content scripts into every page

The Agent Manager and Password Manager declare all_urls host permissions and inject content scripts into http://*/* and https://*/*. This is expected for an AI agent browser — the agent needs page access to read, interact, and act on the user's behalf. Comet, Dia, and ChatGPT Atlas all request similar broad page access.

The verdict

For an AI agent browser, the permission model is expected. Comet, Dia, and ChatGPT Atlas all request similar access — broad page injection, tab control, and native messaging are table stakes for an AI that acts on your behalf. The real concerns are implementation choices, not the permission model itself.

The recovery key entropy is fine (132 bits) — brute-force is not the attack vector. The real trust boundary is that Aside's server holds the recovery entropy. If their backend is compromised, your recovery key is compromised.

The most actionable findings for a security researcher: the empty daemon auth token (#5), the web_accessible_resources exposure (#4), and the capture-tab-without-consent permission (#3). Those are concrete, demonstrable issues that exist regardless of AI agent context.

Could Aside work as a browser extension in other browsers? For an AI agent browser, the Chromium fork approach makes sense — the agent needs deep browser integration that extensions can't provide. But the daemon having no auth token and the server holding recovery entropy are still concerning implementation choices that don't follow from the architecture.
