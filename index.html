The verdict

Your

instinct about "vibe coded" is somewhat validated.

 The permission model is extremely aggressive for what is essentially a 5-person YC startup. The daemon having no apparent auth token, content scripts running on file:///*, and PostHog in a password manager are all red flags for a security-conscious product.

The recovery key entropy is

fine (132 bits) — brute-force is not the attack vector. The real trust boundary is that Aside's server holds the recovery entropy. If their backend is compromised, your recovery key is compromised.

The most actionable findings for a security researcher: the

empty daemon auth token (#5), the web_accessible_resources exposure (#4), and the tabCapture-without-consent permission (#3). Those are concrete, demonstrable issues.

Could Aside work

as a browser extension in other browsers? Technically yes — the password manager and agent could be standalone extensions with narrower permissions. But the current architecture is designed around having full Chromium fork control. Packaging this as an extension would force them to confront how much of their "product" is actually just aggressive permissions that a normal browser wouldn't grant.
